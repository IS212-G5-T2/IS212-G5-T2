# E2E-09: Setup and turnaround boundaries (SPM-50, SPM-56, SPM-51, SPM-54, SPM-55, SPM-52, SPM-125, SPM-121)

Cross-role end-to-end test (executed in CI on 2026-11-06, PR #128). Covers the six-row boundary table from the E2E test plan for a venue with 30 minutes of setup and 45 minutes of turnaround: Event A at 10:00 to 12:00 occupies 09:30 to 12:45, and a second event B is placed against that window in six positions. It crosses the Event Coordinator (who submits), Venue Staff (who approves, or cannot) and the venue calendar, and it is E2E rather than cheaper because the same boundary has to hold on the submission path and on the approval-time recheck. This is the case the plan and SPM-168 single out as the place where AI-written code and AI-written tests are most likely to share a mistake, so every expected value below is worked out by hand from the plan's table and the ACs, never from the conflict query.

**Notes (open questions)**

1. OPEN ITEM, priority: the plan says "P0 for one case" and neither SPM-191 nor SPM-192 names which of E2E-09-A to E2E-09-F is the P0. SPM-168 question 11 lists it as open. This document does not choose. One observation only: row A is blocked on question 1, so it cannot gate a required status check until question 1 is answered.
2. [S1] SPM-168 question 1 (is a booking whose setup starts exactly when the previous booking's turnaround ends allowed? it decides `<` versus `<=`): the case proceeds on "back-to-back is allowed", so row A (effective start 12:45 against A's occupied end 12:45) is not a conflict. Basis on record: SPM-56's note reads occupied periods as half-open [start, end) and says the endpoint rule "is not explicitly fixed ... and needs team/PO confirmation before being treated as customer policy"; SC-SPM159-06 (story owner, 2026-10-28) accepted the exclusive predicate. That is a story-owner decision, not the customer's answer, and the plan itself says "if your customer confirms back-to-back is fine". If the answer is "no", only step 10 and its constant change; rows B to F do not depend on it.
3. Boundary values come from the plan's table and the arithmetic in Test Data (13:15 - 30 min = 12:45; 13:14 - 30 min = 12:44; 12:00 + 45 min = 12:45). No expected value was derived from the conflict query, the availability service or the approval service. Rows C and D overlap by 15 minutes so they stay away from the question 1 boundary; row B is the one-minute-inside case.
4. [S2] RESOLVED 2026-11-06 (SPM-191): pending ordinary booking requests coexist. A new request is blocked only by an approved booking, an active tentative hold or a venue unavailable period, never by another Pending request, so P is accepted next to the still-Pending A (step 1). The race is settled at approval: the approval step re-checks the venue schedule, the request approved first wins, and approving any overlapping Pending request is refused with 409 `BOOKING_SLOT_CONFLICT` naming the winner while that request stays Pending (steps 2 and 3). The Bookings page shows this conflict alert in the approval review. Basis: SPM-56 AC1, AC2, AC4 and AC5 name only approved ordinary bookings and active holds as blockers, and SPM-159 AC8 allows overlapping Pending hold requests; the story-level rule for ordinary pending requests was previously unstated, and the product now follows it. Steps 2 and 3 are reachable through the UI with no controlled fixture.
5. [S3] The refusal status and error code for a conflicting submission and for a conflicting approval are not stated in any AC. The case asserts a 4xx and the stored effect. Take the code from the route's specification when the spec is written, not from the implementation.
6. Plan-versus-story conflict [C1]: the plan says a conflicting request "is flagged before it reaches VS", while SPM-54 AC2 says the coordinator cannot submit it at all. The case asserts the story's stronger form (no row exists) because a flagged-but-saved request would show as a row; the plan's "VS cannot approve a conflicting request" is covered by steps 2 and 3. If the product saves and flags instead, the "no row" assertions in steps 5 to 8 change.
7. Q1 resolved 2026-11-06: back-to-back allowed (half-open intervals, `BACK_TO_BACK_ALLOWED = true`). The half-open reading fixes the setup side too; no row tests that exact edge, keeping the table identical to the plan's.
8. SPM-125 AC4 fixes the touching boundary for unavailable periods only; it is cited as the analogous rule, not as the answer for bookings.
9. Builder gaps: no booking-request builder; the fixture sets event status but not the readiness rows; `db.scene` option names for event start and end are proposed and must be checked against `browser-fixtures.mjs`.
10. SPM-50 AC2/AC5 and SPM-121 AC2 are cited because they define the setup and turnaround settings; this case does not exercise venue creation or editing (E2E-10 does the edit).
11. Existing Confluence pages: `E2E-VENUE-BOOKING-01` (page 33554524) covers the ordinary booking path; no page covers the boundary table. This case complements it and supersedes nothing.
