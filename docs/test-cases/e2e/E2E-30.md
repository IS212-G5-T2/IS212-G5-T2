# E2E-30: Mobile viewport smoke (SPM-36, SPM-37, SPM-61, SPM-97, SPM-99)

Cross-role end-to-end test (DRAFT, not executed). Runs the Event Organiser and Attendee steps of E2E-01 under a Playwright phone profile (the `mobile` project, `devices["Pixel 7"]`, which sets the viewport, touch, device scale factor and mobile user agent) instead of resizing a desktop window. The Organiser creates, saves, reopens and submits an event request and later sees the confirmed arrangements; an Attendee finds a Confirmed event, sees the spots left, registers and sees the status. It crosses two roles and the event-request, planning-view and registration features at phone size. No story states a mobile or responsive requirement; the only source is the plan's reference to a Week 1 design requirement (Notes 1).

**Notes (open questions)**

1. [U11] No story states a mobile or responsive requirement. The only source is the plan's Trace line ("Week 1 design requirement") and its Project documents table, which says the Week 1 briefing lists non-functional rules including "desktop and mobile friendly". The Week 1 briefing itself is not in the repository and was not read. The case therefore asserts what "works on a phone" can mean without inventing a threshold: the existing steps succeed by touch, nothing overflows horizontally, and the primary action is reachable. If the customer states a stricter rule (minimum tap-target size, a specific navigation pattern), add it.
2. The device is `devices["Pixel 7"]`, set by the `mobile` project (SPM-187). Playwright's Pixel 7 descriptor is, from memory and not checked in this session, about 412 by 915, not the 390 by 844 used by the existing `EventCreatePage` spec; both are phone-sized, but the new case must not assume 390. Read the size from the descriptor if a size is ever needed.
3. `pageAs(who)` in `frontend/e2e/fixtures.ts` creates its context from the browser, base URL, locale, time zone and viewport only. It does not copy `isMobile`, `hasTouch`, `deviceScaleFactor` or the user agent. A second user opened that way would get the Pixel 7 viewport but not the touch or mobile user-agent behaviour, so this case runs the Organiser and the Attendee as two test bodies, each signed in through `test.use({ as })`, which does apply the project's `use` options. This was read from the fixture source on the SPM-187 branch, not run.
4. The mobile navigation control (a menu button or similar) is not named by any AC or by the files read. Locate it by role or label once the UI is inspected; do not guess a selector. If the shell offers no mobile control, record that and treat reachability as a finding.
5. The hard rules for this file: it is named `*.mobile.playwright.spec.ts`, it calls no `setViewportSize`, it uses no `page.route`, no fixed sleeps, no `waitForTimeout` and no `networkidle`, and its locators are by role, label or test id.
6. The Organiser's confirmed-arrangements view (E2E-01's last Organiser step, SPM-97 AC2) is checked on a Planning event with an approved booking from the builder because no builder makes a fully Confirmed, ready event (`status: "Confirmed"` sets only the status). It is a Planning event, so the case asserts the approved venue booking is visible, not a Confirmed status.
7. Who is notified is not re-asserted here: it belongs to E2E-01. For the Attendee step, the only expectation is the confirmation message; no AC makes the Organiser or Coordinator a recipient of a registration (assumption S7; see E2E-21).
8. Overlap: Confluence `E2E-EVENT-DRAFT-01` (page 36470866, read in full as the format exemplar) is the desktop Organiser half of the draft and submit steps and is complemented, not superseded, by this case.
9. No DB read helper exists; stored state is read through authenticated API reads. Direct API calls use the saved storage state of the named account.
10. Provenance (surviving manual flows): No surviving equivalent (neither manual suite has a viewport flow). `R<n>` is flow n of the recovered 31-flow `docs/test-cases/ConnectSphere-E2E-Test-Suite.md`; `L<n>` is flow n of the lost 110-flow suite as quoted in SPM-168 comment 10142, which is the only surviving record of it; `A<n>.<m>` is bullet m of original acceptance criterion n in that comment. Source: `docs/prompts/e2e-test-case-generation-brief.md` section 5 (SPM-188 AC5).
11. Automation finding (2026-11-06): the mobile navigation is the sidebar `<aside>` (role complementary, labelled "Primary navigation") slid off-screen until the menu button is tapped, not a `navigation` landmark. Assert it enters the viewport after the tap.
