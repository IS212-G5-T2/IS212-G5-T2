# E2E-10: Changing setup or turnaround flags bookings (SPM-121, SPM-125, SPM-51, SPM-157)

Cross-role end-to-end test (DRAFT, not executed). Covers Venue Staff raising a venue's turnaround time so that two bookings that were valid under the old settings now clash: both bookings must survive, the affected ones must be listed and flagged, and the Event Coordinators concerned must be told, while an unaffected Coordinator is not. It crosses Venue Staff, two Event Coordinators and a third whose booking is untouched, and it is E2E rather than cheaper because the stored bookings, the list shown after saving, the notifications and each Coordinator's booking history must all agree after one real save.

**Notes (open questions)**

1. No AC fixes what "flagged" is persisted as. SPM-121 AC8 and SPM-125 AC8 define a list shown after save and a Coordinator notice; SPM-157 AC2 mentions bookings "returned for review". The plan's "the problem one is flagged" therefore has no stored form that can be asserted. This case asserts only what the ACs define (the list, the notice, the booking surviving, the history entry) and records any stored indicator for the implementer to decide. Open item U10 in the E2E brief.
2. The plan says "the problem one is flagged, and its EC is informed", singular. When a turnaround increase makes two bookings clash, no AC says which one is the affected booking, or whether both are. This was not derived from the implementation. The case asserts that the affected list is non-empty, is a subset of {A, B}, excludes C, and that notifications go exactly to the Coordinators of the listed bookings. If the product answers "both" or "only the later one", state that as the decision and tighten steps 4 and 7.
3. The notification wording for a setup or turnaround change is not given in SPM-125 AC8, so the case asserts recipient, count and link, not text.
4. [S1] Step 8 for coordinator3: SPM-157 AC2 lists "venue changes that affect the booking". Whether a change that does not affect a booking is also written into that booking's history is not stated. Treat the C-side assertion as soft until decided.
5. [S2] The refusal status and error code for an unauthorised venue update are not given in an AC (SPM-121 AC7 says only "cannot edit"). Asserted as a 4xx plus the unchanged turnaround.
6. The clash is 30 minutes so the case does not touch SPM-168 question 1 (back-to-back boundary), which belongs to E2E-09. The new turnaround 60 differs from setup 30 so a swapped field would change the result: with setup 60 and turnaround 30 A would end at 12:30 and B would begin at 13:00 - 60 min = 12:00, still clashing, but the overlap would be 12:00 to 12:30; the list contents are the same, so a swap is caught by the calendar window in step 6 (A to 13:00), not by the list.
7. Builder gaps: no booking-request builder (bookings are created through the UI in step 1), the `coordinatorEmail` option and the event start and end option names are proposed and unverified.
8. Overlapping Confluence pages: none cover venue edit impact (`E2E-VENUE-UNAVAIL-01`, page 36438126, covers unavailability, which E2E-14 owns). This case supersedes nothing.
