# E2E-13: Hold expires (SPM-133, SPM-134, SPM-132, SPM-159, SPM-56, SPM-51, SPM-48, SPM-54)

Cross-role end-to-end test (DRAFT, not executed). Covers a tentative hold reaching its expiry: the Coordinator is reminded 48 hours before and told when it expires, the server stores the hold as expired, the venue frees up so another Coordinator can book it, and the expired hold can no longer be converted. It crosses the Event Coordinator who owns the hold, a second Event Coordinator and Venue Staff, and it is E2E rather than cheaper because the expiry is produced by the backend's own scheduler and has to show up consistently in the database, the notification bell, the venue calendar and the next booking decision. This case is a P0.

**Notes (open questions)**

1. The plan's boundary cannot be written as specified. The plan says "use an injected clock, never a sleep" and "action at T-1 min succeeds, at T+1 min is refused". The SPM-187 clock helper (`freezeClock`, `advanceClock`, `browserNow`) controls the browser only and its own header says the backend keeps real time, so the server's expiry processor and its "now" cannot be moved with `advanceClock`. Writing a step that claims to advance server time through the browser clock would be false, so none is written. What the case does instead: the `holdExpiry` preset seeds expiry relative to real now (47 hours, one minute ago, 10 days) against a one-second scheduler. That proves "one minute after expiry the conversion is refused" at a seeded offset (step 7) and a conversion far from the boundary (step 12). It does not prove "T-1 minute succeeds", and it cannot reach the exact instant T that SPM-56 AC5 and SPM-133 AC2 name ("at or after"). Asserting that boundary needs a server-side clock that does not exist in the harness. The backend does expose an injectable `CLOCK` token, so a controllable server clock is buildable; that is a prerequisite for the implementer, not a decision made here.
2. [S1] SPM-168 question 4 (how long before expiry is the Coordinator warned): the case proceeds on SPM-134 AC1, 48 hours, one reminder, a story-owner refinement of 4 Nov 2026 that SPM-168 still lists as open. The named constant `REMINDER_LEAD_HOURS = 48` gives a one-line edit if the answer changes; the 47-hour seed means the reminder is due immediately only while the lead is 48 hours or more.
3. The plan says "the event no longer counts as having a venue" at expiry. With the preset's three holds on one event, the event still has two other holds, and a hold is never counted as confirmed capacity (SPM-133 AC3), so SPM-54 AC11's summary cannot show a change. No AC says an expired hold stops being counted as a "venue" for the event; SPM-48 AC8 only requires that the dashboard shows active versus expired. Step 9 asserts that, and nothing stronger. Recorded as a gap in the AC set, not asserted.
4. [S2] The refusal status and error code for converting an expired hold, for an unauthorised release, and for a blocked request are not stated in any AC. Assert 4xx and unchanged state; read the code from the route's specification, not from the service. Only the release route `POST /api/venues/bookings/:id/release-hold` is evidenced in the existing spec; the convert route's path was not read and is not named here.
5. [S3] SPM-168 question 8 (a hold blocks outright or only warns) is assumed to be "blocks outright" (SPM-56 AC4, SPM-51 AC7, SPM-159 AC7); step 11 changes if the answer is "warn". Expired holds do not block under either answer (SPM-56 AC5).
6. Timing. The expired notice may arrive up to about a minute after expiry in production because the processor runs every 60 seconds by default; under the harness it runs every second, and the case waits for it with a bounded poll, never `waitForTimeout`. The maximum acceptable production delay is pending Product Owner confirmation (SPM-134 note), so no delay bound is asserted.
7. The notice text shows minutes only; the preset rounds expiries to whole minutes so the text can be asserted exactly. September is rendered `Sept`.
8. Step 14 deliberately uses the browser clock only, for the page's own live label (SPM-133 AC1). It must stay clearly separate from the server-side assertions; also, step 13's absence check is point-in-time only. The database check in that step exists to prove the server was not moved.
9. SPM-134 AC10 (no hold notices for a cancelled event) and AC11 (reminder marked read on release or conversion) are not exercised; the first belongs with cancellation (E2E-28), the second is partly covered by the existing spec's read check. The reminder being unread until opened (SPM-134 AC7) is asserted in step 2 and step 4.
10. Plan-versus-story: none for this journey, apart from the boundary in Note 1. Builder gaps: no builder for hold requests (the preset seeds approved holds directly with SQL); the `coordinatorEmail`, `startInDays` and `durationHours` option names for `db.event` are proposed and must be checked against `browser-fixtures.mjs`.
11. Confluence: the registered ids `HOLD-EXP-NOTIF-06-INT-1` and `-INT-2` (matrix 41582744, case page 41353389) are complemented by this case. The page's pre-conditions still describe the older once-per-run seeding mechanism that `db.preset("holdExpiry")` replaced, per a comment in `browser-fixtures.mjs`; that page needs updating separately and is not changed here.
