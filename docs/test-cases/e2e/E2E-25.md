# E2E-25: Extension into the next booking's turnaround (SPM-85, SPM-65, SPM-56, SPM-64, SPM-51)

Cross-role end-to-end test (DRAFT, not executed). Covers extending an event by one hour so that its turnaround time runs into the next booking at the same venue: the conflict is detected and the change is not silently applied. Run two ways (the Organiser's change request, and the Coordinator's direct edit) plus a one-minute-short control that must not be flagged. It crosses Organiser, Coordinator and Venue Staff (whose two bookings are the evidence) and the change-request, flagged-change and venue-conflict features, and depends on setup and turnaround being part of the occupied period, which a unit test of one module cannot show end to end.

**Notes (open questions)**

1. Boundary rule: expected values are worked out by hand from SPM-56 AC3 (occupied period = start minus setup through end plus turnaround), not read from the conflict query. The extension to 13:00 overlaps by 45 minutes and the control stops 1 minute short. The exact-touch case (A ending at 12:15, occupying until 13:00, exactly B's 13:00) is deliberately not tested here: it is SPM-168 Q1, covered by E2E-09. Q1 resolved 2026-11-06: back-to-back allowed (`BACK_TO_BACK_ALLOWED = true`, half-open intervals).
2. The stories do not word "a change is flagged because it collides with another event's booking at the same venue". SPM-85 AC1 and AC2 test the new value against the event's own bookings ("falls outside a booking's occupied period"), and SPM-65 AC3 previews conflicts "with existing venue bookings". Here A's own booking occupies 09:30 to 12:45, so an end of 13:00 falls outside it regardless of B. The case cannot separate the two causes from the ACs alone; it asserts that B's booking is named among the affected bookings, which is the plan's scenario. If the product lists only A's own booking, decide with the story owner whether the plan or the stories win (the plan wins for expected results by rank). The 12:14 control proves the turnaround is counted: 12:14 is inside A's own occupied period, so it applies, and it is also clear of B.
3. Not decided by any AC: what happens when the Coordinator approves a change request that has a conflict (blocked, or applied and then flagged). The case therefore denies (SPM-65 AC5) instead of approving, and rejects the flagged change (SPM-85 AC4). Confirming the flagged change (SPM-85 AC5) is not run, because the effect on B's booking is unspecified. This should become an open question.
4. Builder gap: `startAt` and `endAt` are proposals; the builder has no time-of-day control. Without it the case must create both events through the product. This is the largest set-up cost in the batch and should be added to the fixture work for SPM-192.
5. Assumption S5: a direct edit of the end time by the assigned Coordinator is allowed in Planning (SPM-49 AC5) and is flagged rather than applied when it conflicts (SPM-85). The edit endpoint `PATCH /api/events/{id}/planning` is taken from the controller's route, not from an AC; the refusal status for the Organiser is an assumption (403).
6. Time zone: the arithmetic is in UTC. The form fields and the schedule are in the browser time zone configured in `playwright.config.ts`; the spec must convert, or fix the zone. If the zone is not UTC, write the typed times accordingly and keep the same 45 minute and 1 minute margins.
7. No builder exists for change requests; the request is created through the Organiser's UI in step 2 (the E2E point). No DB read helper exists; stored state is read through authenticated API reads (`planning`, bookings, venue schedule, change-request audit).
8. Overlap: `E2E-CHANGE-REQ-01` (Confluence page 33554508, a description change only) does not overlap this journey. E2E-09 and E2E-10 cover setup and turnaround boundaries on new bookings and on venue-setting changes; E2E-25 is the change-time variant and complements them.
9. Provenance (surviving manual flows): L42 (generic flagged change). Turnaround postdates it, so otherwise no surviving equivalent. `R<n>` is flow n of the recovered 31-flow `docs/test-cases/ConnectSphere-E2E-Test-Suite.md`; `L<n>` is flow n of the lost 110-flow suite as quoted in SPM-168 comment 10142, which is the only surviving record of it; `A<n>.<m>` is bullet m of original acceptance criterion n in that comment. Source: `docs/prompts/e2e-test-case-generation-brief.md` section 5 (SPM-188 AC5).
10. Automation finding (2026-11-06): (a) as E2E-22, the arrange step must give event A a description and a layout before the planning form will save. (b) Steps 10 and 11 are wrong against the product: the product compares a new time with the booking's HELD window (the event's own 10:00 to 12:00), not with the occupied period, so every extension past 12:00, including 12:14, is flagged as a "window" conflict. SPM-85 AC2 reads "outside a booking's occupied period (including setup and turnaround time)", so by the AC 12:14 should apply at once; the product disagrees. The control is a `test.fixme` and a product defect to raise. The 13:00 extension IS attributed to B and to the turnaround (the venue's setup and turnaround are used), contrary to the earlier suspicion of a fixed 30 minute gap. Step 12 therefore ends with A's end unchanged at 12:00.
