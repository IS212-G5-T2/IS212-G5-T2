# E2E-22: Ordinary edit (SPM-49, SPM-85, SPM-64, SPM-97, SPM-157)

Cross-role end-to-end test (DRAFT, not executed). Covers an ordinary change to a planning event, a description and programme text change, that applies at once with no review and no booking or equipment re-check. The change is made by the assigned Coordinator (the actor is chosen explicitly, see Notes 1), the Organiser sees the updated text, the Organiser cannot make the change directly, and a boundary control shows where "ordinary" ends. It crosses Coordinator and Organiser and the event-information, venue-booking, equipment-reservation and history features; a component test cannot prove that the bookings and reservations are left untouched.

**Notes (open questions)**

1. Actor ambiguity [U6]. The plan's "applies without re-review" is satisfied by a Coordinator's direct edit (SPM-49 AC3, AC5). An Organiser's change request, in contrast, always goes to Coordinator review (SPM-64 AC3, SPM-65), so it can never be "without re-review". The plan does not say which. Decision taken for this case: the actor is the assigned Coordinator making a direct edit (SPM-49 AC3, AC5). The Organiser path is not run here; E2E-27 and E2E-25 cover change requests. If the customer meant the Organiser's request being approved, the case becomes a request, a review and an approval, and "without re-review" no longer holds.
2. The plan says "description or programme text". Only "event description" exists in the stories (SPM-64 AC1); "programme text" is not a named field in any AC. Assumption S2: the programme text is part of the description field or a form field that behaves like it. If the product has no separate programme field, step 5 changes the description only.
3. Assumption S3 (SPM-97 AC5 reads "once the Coordinator resolves a pending change"): a direct edit with nothing pending is visible to the Organiser on the next load. The AC does not state this case explicitly.
4. Step 11: `/events/:id/edit` is guarded to the owning Organiser (route `RequireEventOwner` in `App.tsx`), and SPM-97 AC4 says the Organiser cannot edit information during planning. Whether that route is reachable for a Planning event is not fixed by an AC; record what the page shows and decide with the story owner. Do not assert the code's behaviour until that is decided.
5. Assumption S5: the refusal status for a non-Coordinator update (step 12) is 403; the SPM-168 AC2 wording gives only "refused". Confirm from the SPM-49 matrix.
6. "Triggers no booking or equipment re-check" is observable only as "nothing changed on the booking and the reservation and nothing was returned for review" (SPM-58 AC11 returns requests to Pending Review only for a date or time change). The case asserts the observable outcome, not that a check function was not called.
7. The boundary 100 versus 101 is derived from SPM-85 AC2 ("attendance exceeds a booked venue's capacity"), not from the code. SPM-49 AC5 says attendance applies immediately "when they do not affect existing bookings". If the customer treats equal-to-capacity as unsuitable, step 13 changes.
8. Assumption S8: no notification for an ordinary edit. No AC says any role is notified.
9. No builder exists for equipment requests or reservations, so steps 1 and 2 create them through the product. That makes this case's set-up depend on the E2E-16/17 flows working.
10. No read helper for the database exists. "Stored state" is read through authenticated API calls (`planning`, `history`, `arrangements-status`, the booking and equipment reads).
11. Overlapping Confluence page: none identified for this journey. `E2E-CHANGE-REQ-01` (page 33554508, a description change by change request) was not opened; the brief says it covers a description change only, which is the Organiser path not chosen here, so it complements this case.
