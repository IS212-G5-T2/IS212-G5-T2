# E2E-07: Search and suitability (SPM-52, SPM-54, SPM-51)

Cross-role end-to-end test (DRAFT, not executed). Covers an Event Coordinator searching the venue catalogue from one of their own events, with capacity checked at one below, equal to and one above the venue's capacity, and with each unsuitable venue excluded or flagged for its own reason. Two roles are crossed (Event Coordinator, and Venue Staff who approves the booking that makes one venue busy) and two features (search and the availability rule shared with the calendar). It is E2E rather than cheaper because the "slot already booked" exclusion depends on a booking another coordinator got approved through the real Venue Staff route.

**Notes (open questions)**

1. Plan wording: "Each unsuitable venue is excluded or flagged with its reason." Excluded versus flagged is not fixed by the plan. This case reads SPM-52 AC2 as exclusion in search (capacity, layout, facility, accessibility, slot) and SPM-54 AC1 as a warning on the availability page. If the product shows excluded venues with a reason instead, steps 2 to 7 change from "not listed" to "listed with reason".
2. [S1] Capacity boundary derived from SPM-52 AC2 only ("filter by minimum capacity"): venue capacity 100 passes minimum 99 and 100, and fails 101. SPM-54 AC1 lists suitability warnings for facilities, accessibility and layout but not for capacity, so no AC says a capacity warning appears on the availability page; the case asserts capacity only through the search filter. Not an SPM-168 open question; recorded because the plan's "equal is suitable, +1 is not" has no explicit AC beyond the filter wording.
3. [S2] The refusal status code and error code for a conflicting booking request are not in any AC. The case asserts a 4xx and the stored effect (no row, event status unchanged). The exact code is to be read from the spec of the route when the test is written, not from the conflict query.
4. SPM-52's note says event accessibility needs and venue accessibility features use different values until aligned (SPM-144), and the search maps one to the other. SPM-144 was not read for this case; the facility and accessibility literals in Test Data are placeholders to be checked against the form vocabulary.
5. Step 7 deliberately uses 15:00 to 17:00 rather than a window touching 12:45, so the case does not depend on SPM-168 question 1 (setup and turnaround back-to-back boundary). That boundary belongs to E2E-09.
6. Builder gap: there is no builder for booking requests (per the fixture notes), so step 5 of the pre-conditions creates the booked slot through the UI as coordinator2 and venue_staff1. The `db.scene` option names for venue layouts, facilities, accessibility and the event's requirements are proposed, not verified.
7. The invalid-range checks in SPM-52 AC5 (end not after start, non-positive capacity) are single-screen validation and a stated non-goal; they are not exercised here.
8. Confluence overlap: `E2E-VENUE-BOOKING-01` (page 33554524) covers the booking half and does not cover search filtering. This case complements it and supersedes nothing.
