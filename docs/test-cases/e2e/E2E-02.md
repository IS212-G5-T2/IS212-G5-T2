# E2E-02: Draft handling (SPM-37, SPM-36, SPM-48, SPM-123, SPM-94, SPM-95)

Cross-role end-to-end test (DRAFT, not executed). Covers an incomplete draft saved and resumed with data intact, drafts being invisible to the Lead and to Coordinators, submission with mandatory fields missing being blocked, and a submitted request being visibly distinct from drafts and locked against draft editing. It crosses Organiser, Lead and Coordinator and two features (draft handling and the assignment queue), which is why it is E2E rather than a component test.

**Notes (open questions)**

1. No AC: nothing states that drafts are invisible to the Lead (brief U3b). It follows only from the Lead's queue holding submitted requests (SPM-123 AC1/AC2) and SPM-48 AC3 for Coordinators. The case proceeds on "drafts are not in the Lead's queue and are refused by direct request" ([S1]). The refusal status code is also unfixed; assert refusal and no data. Re-check once the story owner states the rule.
2. [S2] The API status and error code for submitting with a missing mandatory field are not fixed by an AC; the case asserts refusal and unchanged status, with the code marked ASSUMPTION.
3. The plan's "clear message" for missing fields is read as SPM-36 AC5 (each invalid field shows a clear error); exact wording is not asserted.
4. Overlap with existing Confluence page `E2E-EVENT-DRAFT-01` (36470866): this case complements it, it does not supersede it. That page covers the Organiser draft path plus the Coordinator opening the submitted request and its attachment (SPM-38); this case adds invisibility to Lead and Coordinators, the missing-field block (UI and API) and the submitted-versus-draft distinction. Do not retire that page.
5. Note 5 of `E2E-EVENT-DRAFT-01` (SPM-196): the seeded Organiser 1 draft used the key `eventName` so its title did not load; the seed is corrected to `name`. This case avoids the seeded draft by creating its own through the UI; if a seeded draft is later used, re-run against the SPM-196 fix.
6. The failed-save-and-retry behaviour (SPM-37 AC6, 503 injection) is already E2E in `EventCreatePage.playwright.spec.ts` and is not duplicated. That is a permitted fault injection at a named route; this case injects none.
7. Brief provenance: R6; L24, L25 (L20 and L21 are single-screen validation and a non-goal); A3.1. The spec cites `Q2-021`, which is not in the registry.
