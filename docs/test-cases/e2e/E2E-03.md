# E2E-03: Clarification loop (SPM-39, SPM-40, SPM-88, SPM-148, SPM-177)

Cross-role end-to-end test (DRAFT, not executed; one step is blocked). Covers a Coordinator requesting clarification, the Organiser being notified and replying, the Coordinator being notified and approving, and a second round with history kept. It crosses Organiser and Coordinator and the clarification and notification features. The plan's "EO amends and resubmits" step has no acceptance criterion and is not written as a step (see Notes 1).

**Notes (open questions)**

1. BLOCKED step 13: the plan has the Organiser "amend and resubmit" (brief U3). SPM-37 AC7 locks a submitted request against draft editing, SPM-39 covers a reply, and SPM-64 covers change requests; no AC defines an amend-and-resubmit action. The step is not invented. The case covers the loop as it exists (request, reply, resolve, approve). Needs a story or a plan correction. The case can run without step 13, with the Pass/Fail recorded as partial until resolved.
2. [S1] The plan's lifecycle names an "Under review" status; it is not in the implemented status set (Submitted, Approved, Rejected, Planning, Confirmed, Completed, Cancelled). The case proceeds on "the status stays Submitted during clarification" because no story changes it; this is an assumption read from the absence of any status AC, not from the code. If a status is later introduced, update steps 4 to 8.
3. [S2] The SPM-177 notification wording is taken from the bug's agreed text (4 Nov 2026). SPM-177 is a Bug in epic SPM-29, not a Story with numbered ACs; the case quotes its Definition of Done and wording. If the fix has not merged when the case runs, steps 4, 6, 7 and 10 fail by design.
4. [S3] Whether the Organiser is notified when the Coordinator resolves is per SPM-177 (resolve notifies the other party); no SPM-39 AC covers it.
5. No AC says whether a clarification can be sent on an Approved event; SPM-148 AC7 covers Planning only. The case posts only before approval.
6. SPM-168 Q7 resolved 2026-11-06: organiser not notified on assignment. This case is unaffected. Confidence is Medium only because of Notes 1 and 2.
7. Existing Confluence page `E2E-CLARIFY-01` (36503669) overlaps this journey. This case complements it; it adds the second round, the negative cases and the recipient exclusions. Brief provenance: R29, R30; A9.3.
8. Status codes for the refused API calls (steps 2, 9) are not fixed by an AC; assert refusal and no change, code marked ASSUMPTION.
