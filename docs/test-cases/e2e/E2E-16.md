# E2E-16: Reservation reduces availability for overlapping events (SPM-57, SPM-58, SPM-111, SPM-118, SPM-119, SPM-136, SPM-172)

Cross-role end-to-end test (DRAFT, not executed). Priority P1. Event Coordinators request projectors, Technical Support reserves them against a finite pool, and the case proves the pool shrinks only for overlapping events, refuses an over-reservation, ignores units that are not usable, and gives the quantity back when the reserving event is cancelled. It crosses Coordinator, Technical Support and the cancellation flow, and its point is the database effect on the reservation rows.

**Notes (open questions)**

1. Plan versus story [C4]: the plan says units "marked damaged or in maintenance" are not counted. SPM-111 AC6 lists the maintenance statuses as Active, Under Maintenance and Retired; "damaged" is not a status. SPM-119 (retired or damaged equipment) removes equipment through "mark as unavailable", which is a separate action. The case therefore uses an Under Maintenance record and, optionally, a record marked unavailable through SPM-119, and does not assert a "damaged" status. Re-check if a "damaged" state is introduced.
2. SPM-111 records carry a quantity and one status per record, not per-unit rows; "units" in the plan is read as quantity on a non-Active record.
3. No AC fixes whether touching events (A ends 12:00, another starts 12:00) overlap for equipment. The case uses clearly overlapping and clearly separate days only, so it does not depend on that boundary.
4. Whether a refused over-reservation returns an error status or only disables the control is not fixed by SPM-58 AC4; the API status code is ASSUMPTION.
5. SPM-172 puts reservation release on cancellation out of scope of its own notification; the release itself is SPM-136 AC5, used here. The case asserts no notification to TSS on release because no story creates one (SPM-168 AC1 absence).
6. Who may cancel (SPM-168 Q5) resolved 2026-11-06: organiser requests, assigned coordinator decides or cancels directly; Lead cannot cancel. This matches the assumption already in the case. Step 12 is unchanged.
7. Builder gaps: no builders for equipment requests or reservations; the case creates them through the UI. The reserve route name is read from `equipment-requests.controller.ts`; its payload was not checked.
8. Existing Confluence page `E2E-EQUIP-AUDIT-01` (36372554) covers equipment audit records only; this case complements it. Provenance: R23; L65; A7.3 (brief).
