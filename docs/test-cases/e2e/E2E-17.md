# E2E-17: Equipment not available (SPM-58, SPM-172, SPM-57, SPM-135, SPM-129)

Cross-role end-to-end test (DRAFT, not executed). Priority P1. Technical Support cannot provide an equipment request, the Event Coordinator is told and amends it, Technical Support reserves it, and only then can the event proceed to the Safety Officer. It crosses Coordinator, Technical Support, Safety Officer and the confirmation gate, and shows that an outstanding equipment arrangement really blocks the event.

**Notes (open questions)**

1. Plan versus story [C3]: the plan says TSS marks a request "not fully available". SPM-172 states a request is decided as a whole (Reserved or Cannot Provide, no partial reservation, one notification per decision). SPM-58 AC9 phrases the reason per "requested item". The case marks the whole request Cannot Provide and does not assert a partial outcome; if per-item decisions are ever introduced, steps 3 and 10 change.
2. Status naming: SPM-58 AC8 writes "Cannot provide", SPM-172 writes `Cannot Provide`; the case uses the SPM-172 spelling and the exact notification text from SPM-172 AC2.
3. No AC says the Coordinator is unable to request a safety check while equipment is outstanding; it follows from SPM-129 AC1/AC6 (the queue shows only events with confirmed arrangements) and SPM-135 AC2. The expected refusal of `safety-check/request` is therefore ASSUMPTION, and so is its status code. If the application permits the request but keeps the event out of the queue, only step 8's first assertion changes.
4. The positive "event can go to the safety check" depends on the event also having an approved venue booking; the pre-condition states it. SPM-168 Q9 resolved 2026-11-06: preparation and confirmation are separate steps as implemented; there is no `Preparation` status. This case is unaffected.
5. SPM-172 AC7's Confirmed-event refusal is not exercised here because a Confirmed event with an equipment request needs state no builder creates (`status: "Confirmed"` sets status only). Not covered.
6. SPM-172 AC6 (reassignment clears the previous Coordinator's equipment notices) belongs to E2E-06 and is not asserted here.
7. Builder gaps: equipment requests are created through the UI. The update-request route (`PUT /api/equipment/requests/:requestId`) and review routes are read from `equipment-requests.controller.ts`; payload shapes were not checked.
8. Existing Confluence pages: none overlaps directly (`E2E-EQUIP-AUDIT-01` 36372554 is about audit records). Provenance: R24; A7.4 (brief).
