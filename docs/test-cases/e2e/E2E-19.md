# E2E-19: Safety Officer requests changes (SPM-130, SPM-131, SPM-129, SPM-65, SPM-58, SPM-55, SPM-157, SPM-48)

Cross-role end-to-end test (executed in CI on 2026-11-06, PR #128). Priority P1. The Safety Officer asks for changes; the event returns to an earlier planning stage with only the affected arrangement marked for review; the Coordinator revises it; Venue Staff or Technical Support re-approve; the Safety Officer reviews again and approves. The case runs twice, once for a venue-side change and once for an equipment-side change. It crosses Safety Officer, Coordinator, Venue Staff and Technical Support.

**Notes (open questions)**

1. SPM-168 Q9 resolved 2026-11-06: there is no Preparation status. "Returns to the relevant earlier stage" is read as Planning with the affected venue or technical arrangement marked for review (SPM-131 AC4). The case asserts no other status.
2. The plan's "layout unsafe for attendance" is modelled with a layout comment; whether the layout, rather than capacity, is what the Safety Officer can see is covered by SPM-129 AC2.
3. SPM-131 AC4 says arrangements are "marked for review" but does not say how the Coordinator then supersedes a flagged booking: re-approval of the same booking, or replacement and cancellation. The case follows the plan ("EC changes the venue ... VS re-approves") with a replacement venue and cancels the flagged request; this is an ASSUMPTION. The persisted form of "marked for review" is not fixed by an AC (compare U10 on E2E-10); the assertions in steps 3 and 12 that the booking "is no longer approved" and the reservation "no longer Reserved" are read from the behaviour described in SPM-131's note and must be re-checked against the story owner's decision.
4. SPM-58 AC11 concerns a date or time change, not a safety response. It is the nearest AC that states the equipment return to Pending Review; the safety-response trigger is stated only in SPM-131 AC4 ("marked for review") and in the SPM-172 note that changing a request returns it to Pending Review. Do not treat AC11 as covering this trigger.
5. Whether the Coordinator must also mark the feedback item resolved before resubmitting is not in any AC; the status controller exposes a resolve action. The case does not assert it; add it if the story owner confirms. Resubmission requirement is SPM-131 AC6 only.
6. No AC says the Organiser, Venue Staff or Technical Support are notified of a changes-requested outcome (SPM-131 AC1 names the Coordinator). Absence assertions rest on that and SPM-168 AC1.
7. SPM-168 Q6 resolved 2026-11-06: no re-check required for attendance, date or venue changes. This case is unaffected.
8. Run order: run A and run B are independent tests on separate events; the "run twice" requirement is two fresh databases or two scenes, never a shared state.
9. Existing Confluence page: none for the safety outcome. Provenance: R25; L78 (partly covered inside the changes-requested test), L77 (brief).
10. Automation finding (2026-11-06): in run A, cancelling the flagged Hall A booking (step 7) already removes its safety feedback item from the checklist, so step 8's "resolve the feedback" has nothing to resolve; in run B the item is resolved before the resubmission. The Safety Officer's change text box is named "Change" (the first row's label is not "Change 1" for assistive technology).
