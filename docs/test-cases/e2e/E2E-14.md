# E2E-14: Maintenance block on a booked venue (SPM-122, SPM-125, SPM-54, SPM-52, SPM-48, SPM-97, SPM-157, SPM-55)

Cross-role end-to-end test (executed in CI on 2026-11-06, PR #128). Priority P0. Venue Staff blocks a venue that already has a confirmed booking; the event must survive untouched, the booking must be flagged rather than deleted, and only the owning Event Coordinator must be told. The Coordinator then finds and books a replacement and Venue Staff approves it. It is E2E rather than cheaper because the rule "nothing is silently deleted" spans the venue module, the booking table, the event table, notifications and three role dashboards.

**Notes (open questions)**

1. Central rule recorded: nothing is silently deleted. The assertions on the event row and the booking row are the heart of the case and must be database reads, not only UI text.
2. U10 (brief section 9): what "flagged" is stored as is undetermined. SPM-122 AC7 and SPM-125 AC6 define a list shown after save plus a notification; SPM-157 AC2 says a history entry. The case therefore asserts the observable effects (booking row survives unchanged, listed as affected, Coordinator notified, history entry) and does not assert a persisted flag column. Re-check once the story owner fixes it.
3. No SPM-168 question gates this case. Boundary assumption: SPM-125 AC4 fixes the case where an occupied period starts exactly when the unavailable period ends (outside). The mirror edge (a block starting exactly at the occupied period's end, 12:45) is not fixed by any AC; the case does not assert it. The 08:00 to 09:30 / 09:31 pair is derived from SPM-125 AC4 by treating "affected" and "bookable" as the same overlap test; flagged as an assumption.
4. Plan versus story: the plan says "EC searches (V excluded for that slot)". SPM-125 AC3 says the venue "remains searchable" during an unavailable period but cannot be booked. These reconcile only because SPM-52 AC3 excludes venues unavailable for a stated date-time range. The case searches with the slot entered and asserts exclusion; a search without a date range would still list V.
5. The plan says "the event resumes" after the replacement is approved. No AC defines a status transition for this; assumption: the event stays Planning, and the original booking stays approved because SPM-54 AC6 forbids automatic cancellation. The case does not cancel the original booking (the plan is silent). Re-check if the story owner wants the original released.
6. Notification type name and exact text are not asserted beyond SPM-125 AC7 contents (event name, venue, period, reason); the status code for refused requests is ASSUMPTION (409 or 422) unless the API spec fixes it.
7. Absence assertions (organiser1, lead, other coordinators, tech_support1, safety_officer1, attendee1, the acting venue_staff1): no story notifies them; SPM-97 AC3 shows the Organiser the pending change on screen, which is not a notification. If the story owner decides the Organiser should be told, step 5 changes.
8. Builder gap: no builder creates booking requests or an approved venue_bookings row for an event. The case either creates the booking through the UI as set-up steps or lists that builder as a prerequisite. `status: "Planning"` sets status only.
9. Existing Confluence page `E2E-VENUE-UNAVAIL-01` (36438126) overlaps; this case complements it and, once accepted, supersedes it. Provenance: R21; L50; A6.5 (brief). Existing IDs `VEN-UNAVAIL-*` cited by the spec are not in the registry.
