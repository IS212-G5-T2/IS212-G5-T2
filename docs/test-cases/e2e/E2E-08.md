# E2E-08: VS rejects, EC re-books (SPM-55, SPM-54, SPM-137, SPM-148)

Cross-role end-to-end test (executed in CI on 2026-11-06, PR #128). Covers a Venue Staff rejection of a venue booking request, the notification and booking detail the Event Coordinator then sees, and the Coordinator requesting an alternative venue that Venue Staff approves so planning continues. It crosses the Event Coordinator, Venue Staff and (as a non-recipient) a second Coordinator and the Organiser, and it is E2E rather than cheaper because the rejection, the audit row, the notification and the status of the event must agree across real sessions.

**Notes (open questions)**

1. Plan wording: "VS rejects with a reason or alternative". No AC defines an "alternative" field on the rejection; SPM-55 AC3 requires only a reason. The case puts the alternative in the Coordinator's own second request, which is what the plan's next sentence ("EC ... requests the alternative") describes.
2. [S1] After a rejection the event stays in Planning. SPM-148 AC1 moves only an Approved event on its first venue request, and SPM-148 AC3 says later requests do not change the status; no AC returns an event to Approved when its only booking is rejected. If the product does revert, step 7 changes.
3. [S2] The refusal status and error code for a non-managing Venue Staff decision and for a repeat decision are not stated in an AC (SPM-55 AC6 says only "shows an error"). The case asserts a 4xx plus unchanged rows; read the exact code from the route's specification when the spec is written, not from the service.
4. [S3] The seeded owner of the venues is assumed to be venue_staff1, and venue_staff2 is assumed not to manage them (SPM-55 AC1, SPM-121 AC7 "I cannot edit a venue I did not create"). If "assigned to manage" is modelled differently, steps 4 and 5 change.
5. Rejection reason length (SPM-168 question 3: 1 to 2000 versus 10 to 500 characters, three words, real words) is not under test; the reason satisfies every candidate rule.
6. No Technical or Safety role is involved. SPM-137 AC7 (a conflicting or failed decision creates no notification) is exercised only through the refused repeat decision in step 11; the conflicting-decision case belongs to E2E-11.
7. Builder gap: no booking-request builder exists, so both requests are created by the UI. Event status in the Pre-conditions is set by the builder; the Planning transition is asserted from the real first request.
8. Confluence overlap: `E2E-VENUE-BOOKING-02` (page 33620119) is complemented, not superseded.
