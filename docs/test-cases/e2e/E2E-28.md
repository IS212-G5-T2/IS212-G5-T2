# E2E-28: Cancel a confirmed multi-venue event (SPM-136, SPM-155, SPM-162, SPM-171, SPM-138, SPM-58, SPM-54, SPM-65, SPM-157)

Cross-role end-to-end test (DRAFT, not executed). Covers the cancellation of a Confirmed event that holds two venue bookings, an equipment reservation, two registrations and a waiting-list entry: the request path (Organiser requests, assigned Coordinator declines, then accepts), the forbidden actors, the status change, the release of every booking and reservation, the closing of registrations, the notifications to the right recipients and to nobody else, and, the point of the P0, another event taking the same venue and equipment for the same slot immediately. A shorter second event covers the Coordinator cancelling directly. It traces to a Week 1 pain point: cancelled events must not keep holding reservations. It crosses Organiser, Coordinator, Venue Staff, Technical Support, Attendee and a second Coordinator and Organiser.

**Notes (open questions)**

1. SPM-168 Q5 resolved 2026-11-06: organiser requests, assigned coordinator decides or cancels directly; Lead cannot cancel. This matches assumption S1. The actor-refusal assertions at step 6 are unblocked. Confidence is Medium.
2. [U7] The plan says VS, TSS and registered Attendees are notified on cancellation. No story says Venue Staff or Technical Support are notified: SPM-162 and SPM-138 AC12 cover the Organiser, the Coordinator and waitlisted Attendees, and SPM-172 puts reservation release out of scope. The plan outranks the stories for expected results, but asserting a notification no story and no notification type defines would invent one (the Attendee, Organiser and Coordinator notices exist). Assumption S2, recorded both ways: the case asserts the story-backed recipients and asserts the ABSENCE of a notice for Venue Staff and Technical Support. If the customer confirms the plan, those two absences become presences and a notification type must be built first. Registered Attendees are covered by SPM-162 AC3 ("attendees ... still receive the event-cancelled notification as before").
3. Assumption S3: accepting a cancellation request in the UI shows the same strict confirmation as a direct cancel (SPM-136 AC2 says "the cancelling user must confirm"). SPM-155 does not say so for the accept action.
4. Assumption S4: the refusal status for a non-Coordinator cancellation attempt is 403 and for the unauthenticated call 401. The 403 is taken from the existing integration suite, not from an AC; SPM-168 AC2 says only "refused". Confirm from the matrix before the spec asserts a code.
5. "Registrations close" (plan) is not worded as a refusal of new registrations in SPM-136 AC7. The case asserts the Cancelled statuses (AC) and, as assumption S5, that a new registration attempt for a Cancelled event is refused and stores nothing. The exact code is not fixed.
6. Builder gaps: no builder exists for booking requests, equipment requests, change requests, cancellation requests or waiting-list entries; a second venue booking and the equipment reservation are created through the product in the Arrange block. The same-slot starts differ by milliseconds because the builder uses "now plus N days"; a `startAt` option would make them exact. No DB read helper exists; stored state is read through authenticated API reads.
7. "Immediately" is shown by the next action succeeding in the same session. It is not a timed assertion; the backend keeps real time and nothing here waits. SPM-136 AC4 says the venues "show as available for other requests" and gives no delay.
8. Not run: SPM-136 AC9 (events whose date has passed keep reservations until cancelled) and the "cancellation request on a Submitted or Approved event" variants of SPM-155 AC1; they are separate cases.
