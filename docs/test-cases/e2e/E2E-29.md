# E2E-29: Role and relationship access matrix (SPM-30 to SPM-34, SPM-128, SPM-38, SPM-47, SPM-55, SPM-63, SPM-95, SPM-97, SPM-121, SPM-123, SPM-129, SPM-157)

Cross-role end-to-end test (DRAFT, not executed). For each of the seven roles, the forbidden actions are attempted twice: through the UI (control absent, route guarded) and by direct URL or API call as that user, asserting the refusal and that nothing changed in the database. The unauthenticated case is included. It covers access by role (a Venue Staff member cannot approve an event request) and by relationship (an Organiser cannot open another Organiser's event, a Coordinator cannot manage another Coordinator's event). SPM-168 AC2 is the controlling requirement: "a hidden button is not an access control". Route guards are unit-tested in jsdom (`RouteAccess.test.tsx`), which cannot prove the server enforces anything.

Reading the stories shows more: Technical Support approving venues (R10), the Lead approving, rejecting or cancelling (R6), the Attendee viewing internal planning (R3) and the by-role navigation row (R13) are in the same position. 3. SPM-168 Q5 resolved 2026-11-06: Lead cannot cancel. R6's assertion that the Lead is refused is unblocked and confirmed.
4. The route-by-role table is copied from the client route guards in `App.tsx`, which is the code, not an AC. SPM-33 and SPM-34 name landing pages only. Assumption S4: the implemented guard table is the intended design. If an AC elsewhere grants a role a route the table omits (for example Lead access to `/events`, which the plan's "Lead sees all" might imply), step R13 will fail for the right reason and the table should change, not the test hidden.
5. The refusal statuses are not fixed by any AC (SPM-168 AC2 says only "refused" and that protected data is not exposed). 401 for no session is consistent with the existing integration tests; 403 for a wrong role and 403 or 404 for a wrong relationship are assumptions. Assert "status in the refusal set and no protected field in the body" until the matrix fixes the codes, then tighten.
6. Assumption S6: a refused attempt creates no notification. This is asserted generally; only SPM-162 AC6 and SPM-171 AC7 state it for their own notices.
7. Builder gaps: an unassigned event, a pending booking request and a safety check cannot be built, so they are created through the product or listed as prerequisites. The Lead's queue entry is created by the Organiser's submission, which makes R5 depend on the E2E-05 flow working.
8. No DB read helper exists; "stored state unchanged" is established by authorised API re-reads of the affected record before and after each attempt. A read-only `db.query()` helper would strengthen it and is a prerequisite only if raw rows are to be compared.
9. `pageAs` creates a second context with the saved login of a named account; it does not clear another page's cookies, so the multi-account rows do not log anyone out. Only one test body per matrix row is needed.
10. Overlapping Confluence pages: none identified for access; `E2E-COORD-QUEUE-01` (page 36438146) covers the Lead queue assignment (E2E-05) and was not opened for this case.
